# Плагины

Здесь лежат плагины системы оценивания: отдельные способы проверки знаний —
тест, игра, тренажёр, квиз.

## Как установить

1. Скопировать папку плагина в `plugins/`, например `plugins/game/`.
2. Открыть в панели управления «Плагины».
3. Нажать «Включить». При первом включении накатятся миграции плагина, а после
   успеха плагин получит отметку об установке.
4. Если плагин был установлен ранее, но выключен, панель покажет «установлен,
   выключен»; его данные при выключении сохраняются.

Состояние «не установлен» означает, что миграции плагина ещё не завершились
успешно. Если миграции оборвались, проверьте причину ошибки и повторите
включение после исправления.

В `install()` используйте `MyEdu\Plugin\PluginMigrationRunner` для файлов
`migrations/*.sql`. Runner фиксирует каждый оператор: после ошибки повторный
запуск продолжит с незавершённого. Уже выполненные операторы неизменяемы;
исправить можно только ещё не отмеченный оператор, не меняя предыдущие.

Ядро при этом не меняется: новый плагин появляется в системе копированием
папки и одним переключателем.

## Что должно быть в папке

```
plugins/<имя>/
  plugin.json          манифест: id, название, версия, точка входа
  src/                 код плагина (пространство имён из манифеста)
  migrations/*.sql     свои таблицы, накатываются при включении
  templates/           свои шаблоны
```

### Манифест

```json
{
    "id": "game",
    "name": "Интерактивная игра",
    "version": "1.0.0",
    "description": "Что это за способ проверки.",
    "author": "Автор",
    "namespace": "MyEduPlugin\\Game",
    "entry": "src/GamePlugin.php",
    "url_prefix": "games",
    "provides_tasks": true,
    "requires": { "core": "1.0" }
}
```

`id` — строчная латиница, цифры и дефис. Это ключ, по которому плагин
узнаётся в позициях работ, поэтому переименовывать `id` у установленного
плагина нельзя.

`provides_tasks` — даёт ли плагин виды заданий для редактора работы. Читается
из манифеста, а не из кода, потому что выключенный плагин не подключается и
узнать о нём что-то можно только по описанию. Плагин без этого поля всё равно
работает, но в палитре видов заданий его не будет, а редактор скажет об этом
прямо: «тип задания есть, кнопки нет». Иначе плагин, который забыли включить,
выглядел бы как ошибка ядра.

`url_prefix` — адрес, под которым плагин отвечает: маршрут `/{id}` при
`url_prefix: tests` станет `/tests/{id}`. Если поле не указано, берётся `id`.
Адреса внутри плагина стройте через `PluginManager::urlPrefix($id)`, а не
собственным префиксом: иначе плагин разойдётся с ядром после переименования.

`requires.core` проверяется при чтении манифеста по `App::VERSION`; плагин с
несовместимой минимальной версией не загружается и получает понятную причину в
панели.

**Префикс не должен совпадать с системным адресом или закрытым каталогом.**
Зарезервированы `auth`, `classes`, `confirm`, `health`, `login`, `logout`,
`panel`, `portal`, `profile`, `register`, `student`, `work`, `works`, а также
`src`, `config`, `database`, `plugins`, `tools`, `vendor`, `var`, `resources`,
`public`, `assets`, `uploads`. Список в коде — `PluginManager::RESERVED_PREFIXES`,
и README обязан с ним совпадать: проверка `tests/run_http_tests.php` сверяет
объявленные здесь префиксы с настоящими, и расхождение останавливает набор.

`tests` — специальное исключение. Каталог `tests/` лежит рядом с `public/` и
наружу не отдаётся, поэтому префикс `tests` свободен: адреса плагина
`/tests/...` не пересекаются с файлами наборов. Это объясняет, почему он не
закрыт, а не «исключение из правил»: после волны 4 `.htaccess` не перечисляет
закрытые каталоги, а уводит всё вне `public/` внутрь `public/`, где файлов
наборов нет.

Точка входа получает не контейнер, а список сервисов. Это осознанно: контейнер
в руках у чужого кода — это «можно всё», поменять любую настройку и дотянуться
до соседнего плагина. Формально плагин и так исполняется с полными правами, и
об этом честно сказано ниже, но держать в руках то, что не нужно, — значит
отдавать это по недосмотру, а не по замыслу.

```php
public function __construct(private readonly PluginServices $services) {}
```

Через `$services` доступно:

| Что | Зачем |
|---|---|
| `manifest()` | `id`, `name`, `version`, `description` этого плагина из `plugin.json` |
| `database()` | база: `MyEdu\Core\Database` |
| `view()`, `session()`, `csrf()`, `auth()` | то же, что сервисы сайта |
| `config()` | копия настроек; изменение влияет только на копию |
| `dump()` | снятие копии базы перед необратимым изменением схемы |
| `assignments()`, `ratings()` | работы и отметки |
| `ownPlugin(string $id)` | `PluginLocator` этого плагина: `url($path)` и `migrationsDir()` |

`id`, `name` и `version` не пишутся в классе: их возвращает `manifest()`, иначе
плагин со временем назовёт себя не той версией, которая стоит в `plugin.json`.
Идентификатор нужен только для поиска себя в манифесте — больше он ничего не
определяет.

## Безопасность

Плагин — обычная программа на PHP, выполняемая в том же процессе, что и сайт.
Он видит базу и файлы. Включение плагина равносильно запуску на сервере чужой
программы, поэтому включайте только тот код, которому доверяете.

## Контракт

Подробное описание интерфейса `AssessmentPlugin` — в `src/Plugin/`.
Коротко:

| Метод | Зачем |
|---|---|
| `id()`, `name()`, `version()` | Кто это |
| `taskKinds()` | Какие виды заданий видит учитель |
| `routes()` | Свои маршруты под своим префиксом |
| `install()` | Применить свои миграции через `PluginMigrationRunner` |
| `knowsKind()` | Понимаете ли вы этот вид задания |
| `createTask()` | Создание задания по запросу редактора работы |
| `taskEditorUrl()` | Адрес редактора задания |
| `taskData()` | Сырые данные задания из базы плагина |
| `taskDataBatch()` | То же, но сразу для нескольких заданий |
| `canManageTask()` | Проверка, может ли текущий автор редактировать задание |
| `renderEditorFragment()` | Форма редактора для встраивания в работу |
| `renderTask()` | Экран задания ученику |
| `saveAnswer()` | Проверка и сохранение ответа; CSRF проверяет ядро |
| `grade()` | Проверка, возвращает `ItemGrade` |
| `renderReview()` | Разбор для результата |
| `renderSubmitted()` | Ответ ученика для ручной проверки учителем |
| `publicationBlocker()` | Почему задание нельзя выпускать ученикам; `null` — можно |
| `taskPreview()` | Начало условия задания для списков; пустая строка — условия нет |
| `deleteTask()` | Удаление задания вместе с его данными |
| `deleteItem()` | Убрать прохождения снятой позиции работы |

Контракт содержит 22 метода, и все они обязательны: плагин, у которого не
реализован хотя бы один, не загрузится, а причина попадёт в панель.

Для прохождения работы ядро проверяет CSRF до вызова `saveAnswer()`. Плагин
отвечает за проверку формата и допустимых значений собственного ответа.
Вызов `saveAnswer()` окружён DB-savepoint: исключение откатывает частичные
изменения ответа. Ученик остаётся на этом же задании; очищенный от CSRF-токенов
ввод доступен в `AttemptContext::submittedInput` для повторного заполнения формы.
Плагину следует выводить эти значения через обычное экранирование, а после
успешного сохранения ядро удалит временный ввод из сессии.

### О редакторе

`renderEditorFragment()` возвращает HTML формы без оболочки страницы. Ядро
вставляет её прямо в список позиций работы — так автор правит задание, не
теряя из виду остальные позиции. Форма отправляется на адрес, который вы
объявили в `routes()`; после сохранения плагин сам возвращает автора туда,
откуда пришли, по значению `EditorContext::backUrl`.

Отдельного «экрана редактора» в контракте нет намеренно: иначе у каждого
плагина было бы два разных места правки одного и того же задания, и они
разъезжались бы при первой же правке.

### О создании задания

Ядро не знает, чем является задание плагина, поэтому создать его может только
плагин. Учитель нажимает «Создать и добавить», ядро вызывает `createTask()`,
получает номер созданного задания и кладёт на него позицию работы.

`taskEditorUrl()` — адрес, **с которого можно уйти на другую страницу**: он
показывается как ссылка там, где автор вправе уйти. Возвращать `null` нужно,
когда уходить некуда, — например, когда правка идёт прямо в списке позиций
работы, как в `test` и `variable`: там задание правят там же, и второй адрес
только путал бы. Экрана редактирования самого по себе в контракте нет.

`canManageTask()` плагин вызывает сам и обязан возвращать `true` только для
заданий, которыми пользователь вправе управлять: тем же контрактом ядро
пользуется при добавлении существующего задания в работу.

### О публикации

`publicationBlocker()` спрашивает ядро перед выпуском работы: задание готово
к показу ученикам или нет. Возвращать нужно **причину отказа обычным текстом**
или `null`, если всё в порядке. Ядро собирает причины со всех заданий сразу и
показывает их автору на шаге публикации.

Пример:

```php
public function publicationBlocker(TaskRef $task): ?string
{
    $data = $this->repository->find($task->taskId);

    if ($data === null) {
        return 'Задание не найдено';
    }

    if (trim((string) $data['prompt']) === '') {
        return 'В задании не заполнено условие';
    }

    return null;
}
```

Причину видно только автору работы, ученику она не показывается, поэтому в ней
можно писать прямо: «Отметьте правильный вариант ответа», а не код ошибки.

### О данных задания

`taskData()` отдаёт ядру строку задания из вашей базы. Ядро использует её
только чтобы показать название и счётчик, и возвращает вам же в
`EditorContext::taskData` и `AttemptContext::taskData`. Разбирать её ядро не
будет.

### О проверке

`grade()` возвращает балл вашего задания и говорит, ждёт ли оно учителя:

```php
// всё проверилось автоматически
return ItemGrade::scored($score, $maxScore, ['result' => $result->toArray()], $grade);

// автопроверки нет — ждём учителя
return ItemGrade::forReview($maxScore, ['result' => $result->toArray()]);
```

Итог по всей работе с весами позиций считает ядро, а не плагин. Плагин отвечает
только за своё задание.

Если внутри вашего задания хотя бы один вопрос ждёт учителя, верните
`forReview()`: `needsReview` всплывает наверх, и работа целиком уйдёт в
очередь на проверку.

## Как это работает в ядре

Ядро знает о плагине виды заданий, маршруты и умеет спросить у него проверку
`canManageTask()` для защиты редактора и добавления готовых заданий в работы.
Всё остальное — данные и экраны самого плагина.

Список на главной собирается не из плагинов, а из **работ**: ядро показывает
опубликованные работы, доступные пользователю, а позиции внутри каждой рисует
плагин. Поэтому отдельного «списка заданий плагина» в контракте нет.

### Работа

Работа (набор заданий ученику) хранится в таблицах ядра: `assignments`,
`assignment_issues`, `assignment_issue_students`, `assignment_items`,
`assignment_attempts`, `assignment_item_results`.

Попытки заводит сам ученик, когда начинает работу: выдача (`assignment_issues`)
сообщает лишь, что работа ему доступна и до какого срока, и никаких строк в
`assignment_attempts` не создаёт.

Ссылка на задание плагина в позиции работы полиморфная — `plugin_id`,
`task_kind`, `task_id` — и внешнего ключа на неё нет: таблицы заданий у разных
плагинов разные, и номера у них могут совпадать.

Попытка работы тоже принадлежит ядру: у неё свой адрес, свой токен доступа и
свои сроки. Плагину ядро отдаёт `AttemptContext` и забирает `ItemGrade`.

Если плагину нужно где-то хранить прохождение задания, заведите свои таблицы
в `migrations/`. Ссылаться на таблицы ядра не нужно: ядро удалит работу
каскадом, и привязка к её таблицам сломала бы удаление.

Оценивание бывает двух видов: единая оценка за всю работу либо отдельная
оценка за каждое задание со сведением по весам. В обоих случаях итог —
среднее по весам позиций, и это решение владельца проекта.

### Очистка данных при удалении

Ядро сообщает плагину обо всех удалениях, и пропустить их нельзя: номера
заданий хранятся числами, а не внешними ключами, поэтому оставшаяся строка
переживёт удаление задания, и следующий плагин, получивший тот же номер,
покажет ученику чужие ответы.

| Событие | Что вызвать |
|---|---|
| Позиция убрана из работы | `deleteItem()` — убрать прохождения этой позиции |
| Задание удалено целиком | `deleteTask()` — убрать все прохождения задания и его данные |

`deleteTask()` возвращает `false`, если задание ещё где-то используется: ядро
проверяет это сам и не удалит задание, на которое ссылается другая работа.
Прохождения при этом надо убрать **до** удаления самого задания и лучше в одной
транзакции — тогда падение по внешнему ключу не оставит работу без ответов.

## Шаблоны

Шаблон плагина адресуется как `<префикс>/<путь>`, где префикс — `id` плагина.
Имя файла не повторяет папку:

```
plugins/test/templates/show.php        → $view->render('test/show', …)
```

Каталог шаблонов плагина подключается ядром при загрузке плагина, поэтому
отдельных вызовов не требуется. Шаблон может перекрыть одноимённый шаблон
ядра — если на то есть сознательное решение.
