# Миграции схемы

Схема базы опубликована снимком: `database/schema.sql` описывает ровно то, что
стоит на работающих инсталляциях. Новый сервер получает её импортом этого
файла, поэтому история его сборки не нужна и удалена.

Этот каталог — для того, что изменится **после** снимка.

## Правила

- **Нумерация начинается с 001.** Файлы: `001_что_сделали.sql`,
  `002_что_сделали.sql`. Номер задаёт порядок, разбирать его изнутри имени не
  нужно — файлы применяются по имени.
- **Имя файла — это отметка о применении.** Запись об этом файле лежит в
  `schema_migrations`. Переименовать уже применённую миграцию нельзя: файл под
  новым именем будет применён повторно.
- **Изменение обязано попасть и в `database/schema.sql`.** Миграция применяется к
  работающим базам, а свежая установка собирается из снимка. Если изменение есть
  в миграции, но нет в снимке, новая установка поднимется без него — и
  расхождение обнаружится тем позже, чем дальше от места правки.

## Порядок работы над изменением схемы

1. Изменить `database/schema.sql` — это состояние, к которому стремимся.
2. Написать `database/migrations/00N_*.sql`, который приводит к этому состоянию
   базу, стоящую на предыдущем снимке.
3. Прогнать `tools\run_tests.ps1`: наборы идут по базе, собранной импортом
   снимка, и расхождение всплывает сразу.

## Чего файл не должен содержать

DDL, который понимает только MariaDB: `ADD COLUMN IF NOT EXISTS`,
`DROP INDEX IF EXISTS`. MySQL такой синтаксис отвергает, и миграция не
применится ни разу. Повторяемость обеспечивает `SchemaMigrator`: ошибки
1060, 1061, 1091 и 1826 он считает признаком «в базе уже так» и идёт дальше.
